## 真实灾难复盘：NodePort 集体拒连 → kube-proxy「装睡」→ 快照回滚

**现象链**：scale 0→3 后 NodePort 38186 拒连（rc=7）→ endpoints 正常、Pod 正常、Pod IP 直连 ✅、ClusterIP ✅ → 唯独 NodePort ❌ → 排查途中 master1 内存饿晕假死 → 重启后四台 kube-proxy 集体不写规则（master1 `KUBE-SVC=0` 条，worker1 只有 42 条残缺规则）→ Pod 名字反复更换（反复重生）→ 日志零报错「装睡」→ rollout restart / 整机重启洗牌均无效 → **四台统一回滚 a4-lesson3-done 快照 → 满血复活（rc=0）**

**排查中用到的三板斧（B6 核心方法论）**：

| 方法 | 用法 |
|---|---|
| **分层探测** | ① curl PodIP（CNI 层）→ ② curl ClusterIP（kube-proxy Service 层）→ ③ curl NodePort（节点 iptables 层），用「通/不通组合」夹病灶 |
| **对照组** | master1 `KUBE-SVC=0` vs worker1 `=42` → 一台好一台坏，diff 出"局部/全局" |
| **止损回滚** | 日志干净 + 行为异常 + 重启无效 = 状态损坏，诊断到头就回滚，别恋战 |

**结论与疑点**：根因未完全落案（疑似 master1 资源耗尽期间控制面状态损坏 + kube-proxy 读到的配置与 etcd 里完好的 ConfigMap 不一致）。处置方案：考场/训练中若复发 → **四台整机重启或回滚快照**，不恋战。

## 今日新坑（全部亲手踩过）

1. **占位符敲进终端**：`<0:38186>` 尖括号被 bash 当重定向 → syntax error。文档里的 `<>` 是占位，真实值从命令输出读。
2. **测 Ingress 打错端口**：`38186` 是 web 自己的 NodePort；带 `Host:` 头必须打**控制器**端口（31242）。直打 web 也能出页面（nginx 不看 Host），但证明不了 Ingress 在工作。
3. **`localhost:8080 refused`** = 这台机器没有 kubeconfig（kubeconfig 只在 master1）。
4. **`kubectl get endpoints` 报 unknown command** → 用短别名 `kubectl get ep web`。
5. **修完立刻验收 = 抢跑**：组件 Running ≠ 规则/端点已生效，等 10~30 秒再测，看到证据链再下结论。
6. **NodePort 规则只在"接收端口的节点"上**：curl `192.168.184.21:38186` 只需要 worker1 有规则，master1 有没有无所谓。
7. **手滑三连**：`kubect1`（数字1）、`kubecrl`（r/l 邻键）→ 用 **Tab 补全**，kube+Tab 不响=敲错了。
8. **PowerShell 给 Linux 投递命令**：必须单引号包命令，双引号会提前吃掉 `$?`；弯引号从聊天框复制会搅碎命令。
9. **节点假死识别**：控制台没焦点（Ctrl+G）≠ 死机；`ssh uptime` 超时/banner exchange 卡死 = 真饿晕，重启该节点（HA 下 3/2 quorum，集群不死）。
