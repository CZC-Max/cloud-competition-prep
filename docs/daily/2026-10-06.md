**第 5 问的坑（值这 1 分）**：`/etc/sysctl.conf` 里预置了旧的 `net.ipv4.ip_forward=0`（安全基线），直接 append 新行后 `sysctl -p` **旧 0 行把新值盖回去**，且复制的新行带不可见字符报 `cannot stat`。最终 `sysctl net.ipv4.ip_forward` = **0**，不修复就是丢分。

修复三步（也是考场标准动作）：
```bash
grep -n ip_forward /etc/sysctl.conf      # ① 找旧行
sed -i '/ip_forward/d' /etc/sysctl.conf  # ② 全删
echo 'net.ipv4.ip_forward = 1' >> /etc/sysctl.conf   # ③ 手敲重写
sysctl -p | grep ip_forward              # ④ = 1 且无报错才算过
```

🔑 口诀：**`-w` 是临时的，`-p` 才是验货的；conf 有旧值时 `-p` 拿旧值盖新值。**

> 意外之喜：/swapfile 的 2G 交换正好给 2G 内存的 master1 加了兜底，降低「资源饿晕假死」复发概率。

## 今日新知识点

1. **双向宽限期**：kubelet 停 ≈40 秒（node-monitor-grace-period）后节点才 NotReady；修好后也要几十秒才回 Ready。
2. **Pod 状态是 kubelet 上报的**：节点失联后 apiserver 显示的是「最后遗言」（Running），不会立刻 Unknown；**超过 5 分钟驱逐窗口**业务 Pod 开始遭殃 —— 节点故障要抢这个窗口。
3. **Pending 类的判分原文**：`0/4 nodes are available: 1 node(s) had untolerated taint {...}, 3 node(s) didn't match control-plane` —— 一句话说清所有节点为何被排除。
4. **污点语法**：`kubectl taint nodes <节点> key=val:NoSchedule` 加，`key:NoSchedule-` 结尾的 `-` 是去掉，**别漏**。
5. `journalctl -u <服务> -n 20`（`-u` 才是单元级日志，不然刷的是内核网卡日志）。
6. 默认容忍就在 Pod 描述里：`not-ready:NoExecute for 300s` = 驱逐宽限期的出处。
